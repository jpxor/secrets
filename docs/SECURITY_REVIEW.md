# Security review — 2026-10-23

Reviewed source: [`b34074c2770974addd4d9f5681671a59816e40f6`](https://github.com/jpxor/secrets/tree/b34074c2770974addd4d9f5681671a59816e40f6). This is an AI-assisted source review and targeted test exercise, not an independent professional audit or a guarantee that every vulnerability has been found. Links below are pinned to that revision so their line numbers remain meaningful.

**Result:** no application-authored path was found that writes decrypted records or the master passphrase to persistent storage, logs them, or sends them to a backup provider. However, the stronger claim that plaintext cannot escape is false: ordinary text-selection controls expose additional clipboard and external-app paths. Two synthetic-data probes reproduced these paths. The findings below remain open; this review changes documentation only.

## Scope and method

Read the specification, security design, development instructions and progress history. Inspected every current application Dart file, every native Kotlin file, Android manifest/extraction rules, dependency declarations, shrinker rules and existing security/reliability tests. Traced inputs through encryption, persistence, export, backup, recovery, UI, platform channels, clipboard and diagnostics. Searched for network clients, file/preferences writes, logging, text input and selection integration. Also inspected the locally pinned cryptography 2.9.0 implementation and Flutter framework source where application behavior depends on defaults.

No real vault, passphrase, provider configuration, private key or account token was opened. Probes used synthetic in-memory values and mocked platform channels. Website/public configuration and build scripts do not participate in the runtime vault data path. This was not a full dependency implementation audit, fresh vulnerability-database scan, binary/source equivalence assessment, live network capture, device penetration test or review of historical removed transports. It does not cover a modified app, compromised OS, malicious keyboard or already-authorized accessibility service.

## Open findings

Severity here describes the practical exposure in this app, not a formal CVSS score. No critical/high-severity issue was identified within this review's scope; that is not proof of absence.

### SR-01 — Medium: selection copy/cut bypasses sensitive clipboard handling

**Evidence:** [editor text fields](https://github.com/jpxor/secrets/blob/b34074c2770974addd4d9f5681671a59816e40f6/lib/ui/editor.dart#L92-L130), [selectable username](https://github.com/jpxor/secrets/blob/b34074c2770974addd4d9f5681671a59816e40f6/lib/ui/vault_page.dart#L166-L167) and [protected copy implementation](https://github.com/jpxor/secrets/blob/b34074c2770974addd4d9f5681671a59816e40f6/android/app/src/main/kotlin/app/secretskeeper/secrets/MainActivity.kt#L256-L279).

The dedicated secret-copy button calls `copySecret`, which sets the Android sensitive flag and schedules conditional cleanup. Default Flutter Copy/Cut operations call `Clipboard.setData` directly. They do not call this bridge. Revealing a secret in the editor therefore permits a second, unprotected copy path; ordinary username/service fields and visible provider credential fields also retain selection controls.

**Impact:** deliberately selected plaintext reaches the shared OS clipboard without this app's sensitive flag or 30-second cleanup. A clipboard consumer/history feature may retain it. This requires user interaction; no background network exfiltration was demonstrated.

**Reproduce:** use a disposable record, edit and reveal its secret, select text and use the selection toolbar's Copy rather than the vault's copy icon. A widget probe invoked that same `EditableTextState.copySelection` operation, observed `Clipboard.setData` with the synthetic text, observed no `copySecret` call and no second clipboard write after 31 seconds. Physical clipboard retention/preview behavior remains device-dependent.

**Recommended fix:** disable unsupported copy/cut paths or route every permitted copy/cut operation, including keyboard shortcuts and selectable usernames, through one sensitive-clipboard policy. Add behavioral regression coverage for each entry point. The explicit native copy path itself remains best effort: process termination/background clipboard restrictions can prevent its timer from clearing data, and it cannot retract data already read elsewhere.

### SR-02 — Medium: default selection actions can send plaintext to another app

**Evidence:** the same [editor fields](https://github.com/jpxor/secrets/blob/b34074c2770974addd4d9f5681671a59816e40f6/lib/ui/editor.dart#L92-L130) use the default context menu, and the [manifest declares PROCESS_TEXT visibility](https://github.com/jpxor/secrets/blob/b34074c2770974addd4d9f5681671a59816e40f6/android/app/src/main/AndroidManifest.xml#L41-L51). No application context-menu restriction is installed.

Flutter's Android selection integration discovers text-processing handlers and provides sharing. Once a field is unmasked, a selected plaintext value can be supplied to a chosen handler outside Secrets. This includes visible provider credential inputs. An external handler may then store or transmit the value beyond this app's control.

**Reproduce:** install a harmless text-processing handler, reveal/select a synthetic editor secret and choose that handler from the menu. A widget probe mocked handler discovery, selected its generated context-menu action and observed the full selected string in `ProcessText.processTextAction`. The framework's Android plugin puts that string into `Intent.EXTRA_PROCESS_TEXT`. No real external app was launched during the probe. Available menu items depend on installed apps/platform.

**Recommended fix:** install an explicit allowed-action menu for sensitive text, remove Share/Process Text and unnecessary manifest discovery, and test both masked and revealed states. Removing the query alone is insufficient as a policy: other default selection actions also need review. This is an explicit user-initiated disclosure path, not evidence of silent upload.

### SR-03 — Low: service and search inputs retain keyboard suggestion defaults

**Evidence:** [service editor](https://github.com/jpxor/secrets/blob/b34074c2770974addd4d9f5681671a59816e40f6/lib/ui/editor.dart#L92-L98) and [service search](https://github.com/jpxor/secrets/blob/b34074c2770974addd4d9f5681671a59816e40f6/lib/ui/vault_page.dart#L85-L97) disable personalized learning but leave suggestions/autocorrect at framework defaults, unlike username/secret/passphrase fields.

**Impact:** service names and search terms are private vault information too. A keyboard may process these as ordinary text for suggestions. Personalized-learning opt-out is a request to the keyboard, not an enforcement boundary. No keyboard network transmission or disk persistence was observed. Flutter's separate Android spell-check feature is disabled when configuration is absent in the inspected SDK; this review does **not** claim that native spell checking is automatically enabled here.

**Recommended fix:** explicitly disable suggestions/autocorrect for these two fields as well, and verify input flags on a device. A trusted keyboard is still necessary for every field, including masked passphrases.

### SR-04 — Low: cleanup does not cover all transient plaintext/key copies

**Evidence:** [`OpenVault.dispose`](https://github.com/jpxor/secrets/blob/b34074c2770974addd4d9f5681671a59816e40f6/lib/core/vault.dart#L125-L133), [payload serialization/decryption](https://github.com/jpxor/secrets/blob/b34074c2770974addd4d9f5681671a59816e40f6/lib/core/vault.dart#L207-L248), [biometric response copy](https://github.com/jpxor/secrets/blob/b34074c2770974addd4d9f5681671a59816e40f6/lib/app.dart#L119-L131) and [native biometric callback](https://github.com/jpxor/secrets/blob/b34074c2770974addd4d9f5681671a59816e40f6/android/app/src/main/kotlin/app/secretskeeper/secrets/MainActivity.kt#L202-L253).

The owned session key and some temporary key buffers are overwritten. Serialized plaintext bytes, decrypted payload bytes, immutable record/passphrase strings and the original platform-returned biometric key buffer are not comprehensively wiped. Native biometric-enable input is cleared on its success callback's `finally` path, but not explicitly on prompt cancellation/error. Controllers are disposed, which does not prove their old strings are erased.

**Impact:** memory exposure may outlive the visible unlocked state; exploitation requires process-memory/debugger/OS access. No unprivileged remote read path was found. The managed-runtime limitation is already acknowledged in SECURITY.md.

**Recommended fix:** clear owned mutable temporaries on all exit paths, reduce copies and callback retention, and preserve the documented best-effort limitation. Do not promise complete RAM erasure or treat object disposal as proof of it.

### SR-05 — Low: canceled provider setup retains native credential candidates

**Evidence:** [native candidate fields](https://github.com/jpxor/secrets/blob/b34074c2770974addd4d9f5681671a59816e40f6/android/app/src/main/kotlin/app/secretskeeper/secrets/MainActivity.kt#L34-L38), [inspection assigns config](https://github.com/jpxor/secrets/blob/b34074c2770974addd4d9f5681671a59816e40f6/android/app/src/main/kotlin/app/secretskeeper/secrets/MainActivity.kt#L166-L179), [Flutter provider disposal](https://github.com/jpxor/secrets/blob/b34074c2770974addd4d9f5681671a59816e40f6/lib/ui/provider_page.dart#L306-L312) and [disconnect implementation](https://github.com/jpxor/secrets/blob/b34074c2770974addd4d9f5681671a59816e40f6/android/app/src/main/kotlin/app/secretskeeper/secrets/MainActivity.kt#L111).

After a successful connection inspection, native `candidate` retains the supplied configuration, including SFTP credentials. Leaving setup without activation disposes Flutter controllers but sends no native cancellation/clear call. Vault locking and disconnecting the active provider also do not clear this candidate. It remains until activation, another connection attempt or activity/process teardown.

**Impact:** unnecessary credential retention in process memory. No plaintext disk write or network disclosure beyond the selected provider was found. Active workers intentionally need provider credentials in memory; abandoned setup candidates do not.

**Recommended fix:** add explicit candidate cancellation when setup closes, and clear candidate/authentication state on appropriate lock/disconnect/lifecycle transitions. Guard late asynchronous setup callbacks so canceled operations cannot repopulate it. Add a cancellation regression test.

## Verified protections and remaining trust boundaries

- **Encryption at rest:** all record fields and internal record IDs are serialized inside AES-256-GCM payload ciphertext. A separately random 32-byte key encrypts that payload; Argon2id (19 MiB, two iterations, one lane) derives the key that wraps it. Header authentication is separated with `/key` and `/payload`. The library generates fresh nonces when callers omit them; inspected library code uses secure randomness and verifies GCM authentication before returning decrypted bytes. Base64 is only an encoding of ciphertext/metadata.
- **Recovery and persistence:** input size/KDF bounds precede expensive derivation; payload JSON is parsed only after authentication. Restore authenticates before local replacement, and populated or locked local vaults require confirmation in the app. Atomic writes preserve the previous file on ordinary write failure. Native `save` only checks the outer format/version, so encrypted-only persistence relies on the reviewed internal Dart caller; it is not a validator that can distinguish arbitrary plaintext supplied by a modified app.
- **Biometrics:** the Android Keystore AES key requires a strong-biometric-authenticated `CryptoObject`, invalidates on enrollment changes and wraps the actual data key with the vault ID as AAD. A success boolean alone does not decrypt the vault. Hardware-backed/StrongBox protection is not requested or verified for every device. Portable recovery still needs the master passphrase.
- **Background backup:** native workers receive the existing encrypted envelope and separately protected provider credentials. They have no passphrase, biometric prompt or vault-decryption call. Drive URLs are HTTPS with default OkHttp certificate verification; no custom trust-all verifier was found. SFTP pins host keys and rejects unknown/changed keys before authentication. Initial fingerprint approval still needs independent verification by the user.
- **Diagnostics:** current Android log calls emit fixed SFTP stage/reason codes or biometric exception type/stack locations. Provider bodies/raw SSH messages are not logged or persisted. Generic UI errors are fixed messages/class names. No vault-field interpolation into diagnostics was found.
- **Screen, keyboard and accessibility:** `FLAG_SECURE` and screen-off/lifecycle locking are present. They do not conceal plaintext from the chosen keyboard, authorized accessibility tools, a camera or a compromised OS. Revealed secrets and visible service/username text intentionally leave the cryptographic boundary for display. No device-level validation of these protections was performed in this review.
- **Metadata remains visible:** format/KDF parameters, salt, vault ID, ciphertext size, snapshot sequence/time, hashed filename suffix, network timing and provider account/server information are not concealed by payload encryption. Provider credentials must be disclosed to their authentication endpoint as required by that protocol, inside TLS/SSH where applicable; they are not part of portable vault files.
- **Offline guessing and replay:** a stolen backup permits unlimited offline passphrase guesses; the eight-character minimum is not an entropy guarantee. A long randomly chosen passphrase matters. GCM detects alteration but accepts an intact older valid envelope: the portable file has no authenticated monotonic revision/expiry or external freshness anchor. Snapshot ordering/conflict checks help ordinary backup reliability but cannot prove freshness against a malicious provider that replays historical content. Retained backups may contain deleted records.

## Validation evidence

Two temporary widget probes against the actual `EditorPage` verified SR-01 and SR-02 using mocked OS channels and synthetic text. Both passed (meaning they reproduced the reported behaviors). They did not access real clipboard contents, launch another app, contact a provider or decrypt user data. The temporary probe file was removed after execution; the reproduction procedures above describe the same entry points. The inspected Flutter SDK revision was `abaf9c523780a608bd46686fd5e53740a07077f8`; relevant framework implementations are [`copySelection`/`cutSelection`](https://github.com/flutter/flutter/blob/abaf9c523780a608bd46686fd5e53740a07077f8/packages/flutter/lib/src/widgets/editable_text.dart#L2765-L2814), [external context-menu actions](https://github.com/flutter/flutter/blob/abaf9c523780a608bd46686fd5e53740a07077f8/packages/flutter/lib/src/widgets/editable_text.dart#L3269-L3290) and [the Android intent handoff](https://github.com/flutter/flutter/blob/abaf9c523780a608bd46686fd5e53740a07077f8/engine/src/flutter/shell/platform/android/io/flutter/plugin/text/ProcessTextPlugin.java#L63-L96).

These tests do not establish the absence of every plaintext leak. Required project check/build results are recorded in PROGRESS.md with this review's entry.

Maintainer acceptance recorded in earlier progress entries is separate evidence, not a new test performed here.
